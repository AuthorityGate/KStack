Rationale unchanged from round 14: accepting arbitrary HTTPS origins would let a misconfigured or malicious `siteUrl` receive the adopter's Jira credentials. Data Center is an explicit v1 non-goal, consistent with this enforcement and the private-host ban, stated in `--help` and the skill.
- **`projects[]`:** every `projects[].key` non-empty/unique, every `issueTypes[]` non-empty.

An adopter who needs security levels on created issues needs a design revision (a named non-goal for v1), not a config knob. - **`credentialSource`:** matches exactly one of the two variants above (no `keychain` variant present in v1 at all). For the `file` variant, **`path` is validated at load, fail-closed (round-15 fix, Opus SEC-1 — this was previously unenforced prose, the identical defect class round 14 fixed for `siteUrl`):** `path` must be absolute, and `realpath(path)` must not be inside `realpath(<repo root>)` (prefix comparison on the resolved paths with a trailing-separator guard) — violation ⇒ config invalid, exit 1. This is enforcement, not advice: a credential file inside the working tree is commit-eligible (§8's `.gitignore` entry covers only `.kstack/jira-queue/`). The existing checks are unchanged: existence, regular non-symlink file, owned by the invoking user, mode grants no group/other access → otherwise config invalid (exit 1); on filesystems that don't enforce POSIX modes (e.g. `/mnt/*` drvfs mounts — this repo's own filesystem), the permission check will typically fail unless the file lives on a POSIX-honoring mount, or the adopter explicitly sets `allowInsecurePermissions: true`, which `doctor` then flags loudly on every run. `allowInsecurePermissions` relaxes only the mode-bits check — never the absolute-path/outside-repo/ownership/symlink checks.
- **Well-formedness:** every string leaf AND every object key within a `defaultFields` value tree, plus every `staticLabels` entry, must satisfy `String.prototype.isWellFormed()`, checked recursively at load time.

**State machine — complete edge list (round-15 fix: three previously omitted load-bearing recovery edges are now listed; this list is authoritative and every edge referenced anywhere in this document appears in it):**

| Edge | Actor |
|---|---|
| `pending → approved` | `approve` |
| `approved → pending` | `unfreeze` (audit-logged) |
| `approved → submitting` | `submit` (the guarded pre-POST write, §4.10) |
| `submitting → submitted` | `submit` (2xx with key) or `reconcile` (recovery, §4.10) |
| `submitting → failed` | `submit` (definite non-retryable response, §7) |
| `submitting → unknown` | `submit` (ambiguous response, §7) or `reconcile` (recovery, no covering sidecar, §4.10) |
| `submitting → approved` | `reconcile` recovery with definitive `posted:false` sidecar evidence (§4.5/§4.10 `aborted-before-post`) |
| `unknown → submitted` | `reconcile` (exactly one match, §7) or `resolve` entry state (a) |
| `unknown → approved` | `reconcile` (zero matches after visibility-checked full poll, §7) |
| `pending → submitted`, `approved → submitted`, `failed → submitted` | `resolve` entry state (c) — human-attested stale-holder duplicate (§4, §4.10) |
| `pending → discarded`, `failed → discarded` | `discard` (subject to the §2 guard and the §4.10 gate) |

States, annotated:

- `pending`: unfrozen (`canonicalPayload === null`) or frozen. Editable via `edit` (clears the freeze). Discardable — **unless refused by the ambiguous-history guard** (below) or the §4.10 pre-discard gate.
- `approved`: frozen + human-confirmed, `approvedAt` set. Reversible to `pending` via `unfreeze` (audit-logged) — the recovery path for config drift or expired approval.
- `submitting`: written immediately before the POST, in the same guarded write that atomically appends the `attempts[]` row (`outcome: "in-flight"`, §4.10).
- `submitted`: confirmed success (via `submit`, `reconcile`, or `resolve`), `result` populated. `reconcile` remains valid in verify mode (§7) when triggered (§4.10).
- `failed`: definite non-retryable outcome. Terminal **except** for the single human-attested edge `failed → submitted` via `resolve` entry state (c) (round-15 fix — "strictly terminal" was inconsistent with the coverage `failed` needs; see the gate/resolve coverage note below). Normal recovery is `discard` + a fresh `draft --from <uuid>` (clones content, new UUID/label).
- `unknown`: ambiguous outcome. Requires `reconcile` before further action. A multiple-match reconcile stays `unknown` (never auto-discardable) unless resolved via `resolve` entry state (a).
- `discarded`: from `pending`/`failed` only.

**`attempts[]` cardinality — single authoritative definition (round-15 fix; this wording governs, and §4.5/§4.8/§4.10 now reference it rather than restating it):** **exactly one `attempts[]` row per `submit` invocation that successfully persists the `approved → submitting` transition.** Consequences, spelled out:

- A dry run (§4), an invocation stopped by any pre-send check (exit 8, 9, or 15), and an invocation fenced *before* the `submitting` write create **no** row.
- A single row-owning invocation may make multiple physical POSTs internally (429 backoff retries, §7); the intermediate attempts are logged to `audit[]` (`{event: "retry-backoff", at, httpStatus, waitMs}`); the row records that invocation's *final* outcome only, created `in-flight` at the `submitting` write and updated exactly once, mapped 1:1 from §7's classification table (`submitted` → `success`; `failed` → `failed`; `unknown` → `ambiguous`).
- Row schema: `{attemptId, lockId, startedAt, outcome}` — **`lockId` (the writing invocation's lock acquisition, §4.2) is recorded in the row, and `attemptId` is recorded in any sidecar the same invocation later writes (§4.8), so a sidecar can be correlated to the row it covers by `attemptId` with `lockId` as cross-check (round-15 fix, Codex: previously "the sidecar covering the in-flight `attemptId`" was asserted with no durable identifier linking the two — a late sidecar from an older stale holder could be associated with the wrong attempt).** A sidecar with a missing or mismatched `attemptId` does not cover any row; it folds as `stale-holder-outcome` evidence only (§4.7), and an uncovered `in-flight` row resolves per §4.10's no-covering-sidecar rule.

**Fenced-invocation exception, clarified:** a process that discovers it is fenced *before* attempting the `submitting` write cannot author an `attempts[]` row at all — its outcome is recorded via a sidecar file (§4.8), folded into `audit[]` as `stale-holder-outcome` by whichever process later holds the lock (§4.7). This is distinct from the narrow §4.5 residue case: if the `submitting` write's rename physically lands *before* the post-write fence recheck discovers the mismatch (the disclosed microsecond race), the `in-flight` row genuinely exists on disk despite the process being fenced at that instant — this is not a violation of the cardinality rule (the transition did persist), it is the already-disclosed residue, and that row's presence is exactly what lets `reconcile` complete it later (as `aborted-before-post` if a `posted:false` sidecar with matching `attemptId` confirms no POST occurred, or otherwise via the normal §4.10 recovery procedure). A `reconcile` recovering a persisted `submitting` draft *completes* that draft's existing `in-flight` row (never creates a new one). A `resolve` transition to `submitted` (any entry state) synthesizes no `attempts[]` row — for entry state (c), any prior `failed` row stands untouched as history, and the evidence of the stale holder's POST lives entirely in `audit[]`.

**Ambiguous-history discard guard:** `discard` is refused (exit 14) whenever `attempts[]` contains an `ambiguous` outcome that has not been cleared by a `verify-confirmed` audit entry (exact single-match verify-mode result, §7) or a `duplicate-acknowledged` audit entry (human-resolved duplicate, §4/resolve) — checked against `attempts[]`/`audit[]` history regardless of the draft's current state, so the `unfreeze`→`pending`→`discard` path cannot bypass it, and it applies equally to `discard` from `failed`. A human who wants to discard anyway passes `--acknowledge-ambiguous-history` (required, audit-logged: `{event: "ambiguous-discard-acknowledged", at, priorAmbiguousAttempts}`). **This flag has no separate "clearing" semantics:** it is a one-time override that permits `discard` to proceed despite the unresolved ambiguity, not a claim that the ambiguity is resolved. There is nothing further to clear because `discard` is terminal — once the draft is gone, the guard has no further draft state to gate; the acknowledgment's only lasting effect is the permanent audit-trail record of the override. A bare `submitted` transition alone does **not** clear the guard — only an explicit `verify-confirmed`/`duplicate-acknowledged` entry does, since a submitted transition following an ambiguous attempt is exactly what verify mode exists to double-check, not proof by itself. **This guard (keyed on `attempts[]`) is independent of §4.10's pre-discard/pre-unfreeze gate (keyed on `audit[]` evidence of a lock break) — each has its own clearing entries, and clearing one never clears the other. Nothing in round 16's marker-lifecycle changes (§4.10) alters this guard's clearing list.**

## §3. Canonicalization and authentication (final)

JCS is not used. Exactly one process ever serializes the payload (at `show`/freeze time); the resulting bytes are persisted verbatim in `canonicalPayload` and every later operation reads and re-hashes those same bytes, never reconstructing them. Fields object built in code with fixed key emission order `[project, issuetype, summary, description, labels, ...defaultFields keys in adopter-configured order]` — no collision with the six reserved keys is possible since §1 bans them from `defaultFields`. **The unit hashed, stored, and transmitted is the UTF-8 encoding**: `payloadBytes = Buffer.from(JSON.stringify(fieldsObject), 'utf8')`, `payloadSha256 = sha256(payloadBytes)`, POST body is `payloadBytes` with `Content-Type: application/json; charset=utf-8`. `canonicalPayload` stores the JSON string form (lossless because §2 rejects non-well-formed input); `submit` re-verifies `sha256(Buffer.from(canonicalPayload,'utf8')) === payloadSha256` before sending — mismatch is an internal-consistency error, exit 15, state left unchanged (`approved`), flagged for investigation, not blind retry.

**Authentication:** HTTP Basic auth, per Jira Cloud's documented REST v3 contract. The resolved `email`/`token` pair (from `credentialSource`, §1/§6) is combined as **`base64(utf8Bytes(email + ':' + token))` — the base64 input is explicitly the UTF-8 encoding of the concatenation (round-15 fix, Opus SEC-3: the byte encoding was previously unstated in a document otherwise explicit that the transmitted unit is UTF-8; a non-ASCII email must not produce an environment-dependent header)** — and sent as `Authorization: Basic <that value>` on every request (`show`'s createmeta calls, `submit`'s POST, `reconcile`'s search, the §7 `mypermissions` precheck). The resolved email is **trimmed of surrounding whitespace exactly once, at credential-resolution time, and that trimmed value is used verbatim in both this header and §6's `configFingerprint`** (round-15 fix, Opus SEC-4 — the fingerprint previously lowercased what the wire did not, so two configurations differing only in email case/whitespace fingerprinted identically while authenticating differently, defeating exactly the drift detection §6 exists for). An email containing `:` is rejected at credential resolution (Basic auth cannot represent it unambiguously). Header construction happens in exactly one function — the same single choke point §6 already requires for reading the credential. **What that centralization buys, stated precisely (round-15 fix, Codex SEC-AUTH-MEMORY-CLAIM — the previous text overclaimed):** it does *not* and cannot prevent transient copies existing in memory (Basic construction necessarily materializes the raw token, the concatenation, and the base64 form); what it provides is a single audited construction site and a single value shape for the shared redactor (§8) to know about. The header value must be redacted in any diagnostic output exactly like the raw token itself, since it trivially decodes back to it.

### §4.1 Scope of the guarantee — stated honestly, up front

The lock protects exactly one thing: the local state of `.kstack/jira-queue/<uuid>.json` (draft + `attempts[]` + `audit[]`) against lost updates and torn writes from concurrent local processes. It does not and cannot fence the external POST to Jira; Jira has no knowledge of the lock, and any claim that a local mechanism prevents a resumed stale process from completing a POST is rejected by construction. The external side effect is handled by detection (§4.8, §4.10), never by claimed prevention. The local guarantee carries disclosed microsecond-scale residues — the §4.5 guarded-write residue, the §4.9 release-claim residue, and the §4.6/§4.9 check-then-rename overwrite residue — all enumerated in §8 **with their honest failure directions, including the dirty case (see §4.6's round-16 rewording).**

### §4.2 Lockfile: path, content, acquisition

- Path: `.kstack/jira-queue/<uuid>.lock` (sibling of the draft). Same commands require it as before (all draft mutations; read-only commands only where §4.10 gates write audit).
- **Acquisition — publish-then-link (universal, closes the empty-lockfile window):**
  1. Create `<uuid>.lock.tmp.<lockId>` with `O_CREAT|O_EXCL|O_WRONLY`, mode `0600`; write the lockfile JSON object (below); `fsync`.
  2. `link(<uuid>.lock.tmp.<lockId>, <uuid>.lock)` — atomic publication, fails `EEXIST` if the path is occupied. The content is complete *before* it becomes visible: **there is no empty/partial-lockfile window.** On success, unlink the tmp name; retain the open fd (same inode as the published lock). Directory `fsync` after the link and after the unlink (§4.7 durability rules).
  3. On `EEXIST`: unlink your own tmp file first (hygiene), then read/`stat` the existing lock: mtime age ≤ `LOCK_STALE_MS` → live → exit `EXIT_LOCK_HELD` (16), naming the holder; age > `LOCK_STALE_MS` → break protocol (§4.6).
- Lockfile content: `{lockId (random 128-bit per acquisition), pid, hostname, acquiredAt, op, stateAtAcquisition, brokePrevious}`. `op`/`stateAtAcquisition` let a later tombstone (§4.6) self-describe whether the broken lock was held by an in-flight `submit`.
- **Empty/unparseable existing lockfile** (foreign junk — the publish-then-link idiom cannot itself produce one): cannot belong to a fence-passing holder, since every fence check requires content-`lockId` equality and even the file's own writer would fail it. Still wait out `LOCK_STALE_MS` before breaking (conservatism against non-conforming writers); the break protocol's observed identity is then `(dev, ino, size, mtime)` in place of `lockId` (§4.6).

### §4.3 Heartbeat — liveness signal only

An async interval timer fires every `LOCK_HEARTBEAT_MS` and calls `futimes(fd)` on the held fd — updating mtime on the inode the holder owns. It never rewrites content, never unlinks, never renames, never re-creates (an unlink-then-create idiom was tried and rejected in an earlier round — it destroyed the mutual exclusion it claimed). The heartbeat runs identically during 429 backoff sleeps, the in-flight POST, and reconcile's bounded poll, and **runs until the release-rename of §4.9 step 2 completes** (not merely until release begins). If the lock was renamed/unlinked out from under the holder, `futimes(fd)` still succeeds harmlessly against the orphaned inode — heartbeat failure is never load-bearing; fencing is done by the path checks in §4.5.

**Normative implementation constraint:** while holding a lock, no synchronous blocking operation may exceed `LOCK_HEARTBEAT_MS` — no sync sleeps, `Atomics.wait`, `spawnSync`/`execSync`, or long synchronous fs calls. All waits (backoff, polls) must be async timers that yield the event loop. Violating this starves `futimes` and manufactures false-stale breaks during in-flight POSTs; §4.10's detection is the backstop for that scenario, not a license to cause it routinely.

### §4.4 Constants

`LOCK_HEARTBEAT_MS = 5000`. `LOCK_STALE_MS = 90000` (18 missed beats). Code constants, not adopter config — deliberately unrelated to `timeoutMs`, `maxAttempts`, backoff, or reconcile budgets, since a live heartbeat covers any legitimate operation length by construction, not by arithmetic. 90s is generous against event-loop stalls, GC, and coarse filesystem mtime granularity. A process silent for 90s is dead or suspended — both are what the break protocol and detection layers exist for. System-wide suspend causes at worst a false break on resume (the safe direction).

### §4.5 Fence checks and the guarded-write primitive (all draft mutations)

Every draft write by every command:

1. **Fence check:** open `<uuid>.lock` by path, read content, compare `lockId` to own (plus `(dev, ino)` comparison where reliable). Mismatch or read failure ⇒ fenced — must not write the draft (§4.8).
2. **Write:** temp-file + `fsync` + `rename` over `<uuid>.json` + directory `fsync` (§4.7).
3. **Post-write re-check:** repeat the fence check. Mismatch ⇒ stop, write an orphan sidecar (§4.8) reflecting reality, exit per the corrected semantics below.

**Exit semantics (17/18 distinguish residue, not "was a POST sent"):**

- `17 EXIT_LOCK_FENCED_CLEAN` — fenced with **no residue**: no unrecorded POST, and no draft write landed after losing ownership. The draft on disk fully reflects what happened.
- `18 EXIT_LOCK_FENCED_DIRTY` — fenced with **residue**: a post-fence draft write may have landed, and/or an unrecorded POST may have occurred. The sidecar's `{posted, wroteAfterFence}` fields (§4.8) carry the specifics — callers must consult the sidecar, never infer POST status from 17/18 alone.
- `posted` means "an unrecorded POST **may** have occurred," not "a POST was ever sent." A `submit` whose POST and response were fully recorded in the draft before it was fenced (e.g. fenced only at release, §4.9) writes `{posted: false}` and exits 17 — the draft already tells the whole story.
- Post-write re-check failure on an **offline** mutation (`edit`, `approve`, the pre-POST `submitting` write) ⇒ exit 18, sidecar `{posted: false, wroteAfterFence: true}`. Because this sidecar is authored after the invocation ceased all mutation, `posted: false` here is *definitive* no-POST evidence: on folding it, `reconcile` marks the affected `in-flight` attempt row (matched by the sidecar's `attemptId`, §2) `aborted-before-post` and returns the draft to `approved` (`submitting → approved`, a listed edge in §2) — deterministic recovery, no `ambiguous` outcome, no mandatory verify from this alone.

**Stated residue:** step 2's rename is by path and can't be conditioned on step 1's result; a process suspended between check and rename for longer than `LOCK_STALE_MS` can clobber a successor's write. Requires suspension onset inside a microseconds-wide window *and* duration >90s — disclosed, not claimed away. The post-write re-check makes the clobber self-reported via sidecar rather than silent.

Same fence check runs immediately before initiating the POST and immediately after receiving the response in `submit` — best-effort duplicate-window reduction, not prevention.

### §4.6 Stale-break protocol — atomic claim via tombstone rename

1. Record observed identity (`lockId` = X, mtime). Re-`stat` immediately before step 2; if mtime advanced, holder is alive → abort, exit `EXIT_LOCK_HELD` (16).
2. **Claim by rename:** `rename(<uuid>.lock, <uuid>.tombstone.<breakerId>.json)` — atomic; for a given inode exactly one breaker's rename succeeds. `ENOENT` ⇒ another breaker won ⇒ restart acquisition (§4.2).
3. **Verify the claim:** read the tombstone. `lockId == X` → correct lock broken; leave the tombstone (self-describing), proceed to acquire fresh via §4.2, recording `brokePrevious: {lockId: X, ...}`.
4. **Mis-claim path:** tombstone's `lockId ≠ X` (a double-break interleaving) → **check the `<uuid>.lock` path is absent, then `rename()` it back.** This check-then-rename is an accepted design tradeoff: Node's `fs.rename` has no atomic `RENAME_NOREPLACE`, so there is a TOCTOU gap in which a third process's freshly-created lock can be overwritten. Requiring a native `renameat2` binding to close this fully was judged not worth the added native-dependency surface for a window this narrow. **The failure direction, stated honestly (round-15 rewording — the previous "at worst a falsely-fenced clean abort" understated it):** in that window, a third process's lock genuinely *is* destroyed; the safety property is not that the lock survives but that the victim self-reports — its next fence check reads content that is not its own and it aborts per §4.8. That abort is *clean* (exit 17) if the victim had no unrecorded work, but **can be dirty (exit 18, with sidecar)**: a victim that had passed its last fence check before displacement may have completed a draft write or initiated a POST inside the window, and the sidecar's `{posted, wroteAfterFence}` fields then carry exactly that residue. What the design guarantees is *never a silent correctness violation* — every such outcome is self-reported through the sidecar/janitor machinery and lands in the §4.10 detection triggers; it does not guarantee the outcome is always clean. If the rename-back fails or the path is occupied, leave as a tombstone, exit `EXIT_LOCK_BREAK_RACE` (19).
- **No-lockId case:** where the observed lockfile was empty/unparseable (§4.2), the observed identity is `(dev, ino, size, mtime)`; step-3 verification compares by `stat` of the tombstone. Breaking an unparseable lock is safe regardless: no process can pass a fence check against unparseable content, so the worst case is a break of a lock nobody could use.
- **Invariant (restated honestly):** *at any instant, at most one process's fence check against the current `<uuid>.lock` content can pass* — lockIds are unique per acquisition and the path has exactly one content. An interleaving may transiently leave two processes each holding an open fd (e.g. during the mis-claim window the path is briefly vacant and a fresh §4.2 acquisition can succeed while the displaced holder still holds its fd) — but never two processes that both pass fence checks, so every subsequent guarded write self-arbitrates. In the rename-back-succeeds sub-case the displaced holder's next fence check correctly **passes** — that is recovery, not a violation. Races resolve to fenced aborts (clean or dirty, both self-reported) or a restored holder — never to a silent violation.

### §4.7 Janitor — folding tombstones, sidecars, and release leftovers

First draft operation after every lock acquisition, before the command's own work: sweep this draft's `<uuid>.tombstone.*.json`, `<uuid>.orphan.*.json`, `<uuid>.released.*.json`, and stale `<uuid>.lock.tmp.*` litter. `status` and `reconcile` additionally sweep the whole queue dir (including `discarded` drafts), folding by briefly acquiring each affected draft's lock.

- **Classification:** tombstones → `lock-broken`/`lock-break-race`; orphan sidecars → `stale-holder-outcome`. `released.*` files: content `lockId` matching the filename `lockId` ⇒ a crash between §4.9's rename and unlink — a clean, deliberate release; folds as `{event: "lock-released-late"}`, benign, does **not** arm §4.10 trigger (b). Mismatched `lockId` ⇒ a §4.9 mis-claim leftover; folds as `lock-break-race`. `*.lock.tmp.*` files older than `LOCK_STALE_MS` are crashed-acquirer litter: deleted without folding (never published).
- **Durability — normative rules (round-15 change: directory `fsync` moves from open item to requirement):** orphan sidecars are written temp-file + `fsync` + `rename`, mode `0600` — same idiom as `<uuid>.json`; lockfiles and tmp files are `0600`; tombstones/`released.*` files inherit the fsync'd lockfile content via rename. **Every `rename`, `link`, and `unlink` in §2's, §4.2's, and this section's write paths is followed by an `fsync` of `.kstack/jira-queue/`'s directory fd** — without it, the rename's durability is not guaranteed to survive a crash on some filesystems, which would undermine §8's layer-1 "deterministic given sidecar durability" claim. On filesystems where directory `fsync` is a no-op or unsupported (possible on drvfs — empirical verification is an open item), durability degrades to that filesystem's native guarantee and §8's layer-1 framing is correspondingly conditional; this is disclosed there.
- **Fold ordering and idempotence:** append the audit entry via the guarded-write primitive + `fsync`, **then** unlink the folded file (+ directory `fsync`). Folds are idempotent, keyed by the folded file's `lockId` + event type — if a matching audit entry already exists, skip straight to unlink. A crash between fold and unlink duplicates nothing and loses nothing; evidence (including a `posted: true` issue key) cannot be torn away by the janitor cycle.
- Load-bearing ordering unchanged: a `submit`/`reconcile` transitioning a draft to `submitted` must fold before that transition — a break is never "not yet folded" at §4.10's trigger-evaluation time.

### §4.8 Fenced/resumed-holder behavior — fully defined

- Sidecar path `<uuid>.orphan.<lockId>.json` (uniquely owned, uncontended); schema `{lockId, attemptId?, at, op, posted, wroteAfterFence, responseClass?, issueId?, issueKey?}` — **`attemptId` is present whenever the writing invocation was a `submit` that had generated one (it is generated before the `submitting` write, so even a fenced-before-write submit records it); absent for non-submit ops.** It is the durable correlation key to the `attempts[]` row (§2, round-15 fix). Written via the §4.7 idiom (temp + `fsync` + `rename` + directory `fsync`, `0600`).
- Exit code per §4.5's semantics: no residue ⇒ 17; any residue (`posted: true` and/or `wroteAfterFence: true`) ⇒ 18.
- The sidecar is the durable handoff mechanism: written by the process with the information, at a path it uniquely owns, folded into `audit[]` by whichever process later holds the lock. A `posted: true` sidecar bearing an issue key is direct, deterministic duplicate evidence and **arms §4.10's gate immediately on folding, with no search required** (§4.10's direct-evidence rule).
- **`attempts[]` rule (per §2's authoritative cardinality definition):** a fenced invocation never authors or completes an `attempts[]` row; its record is the sidecar, folded as a `stale-holder-outcome` audit entry.

### §4.9 Release — rename-claim protocol

1. Heartbeat still running. Fence check by content (§4.5); mismatch ⇒ skip removal entirely, write sidecar, exit fenced per §4.8.
2. `rename(<uuid>.lock, <uuid>.released.<lockId>.json)` — atomic claim of whatever inode occupies the path. `ENOENT` ⇒ another process broke or claimed the lock ⇒ treat as fenced: write sidecar (`posted` per its true definition — usually `false` here, since everything was recorded), exit per §4.8. Heartbeat stops only after this step. Directory `fsync` after the rename (§4.7).
3. Read the renamed file. Content `lockId` == own ⇒ unlink it (+ directory `fsync`; no audit entry needed — nothing was broken), stop heartbeat, close fd. Done.
4. Content `lockId` ≠ own — the resumed-releaser race: this process claimed a *successor's* lock. Check-then-rename it back to `<uuid>.lock` if that path is absent — same accepted check-then-rename tradeoff as §4.6 step 4, **with the same honestly-stated failure direction: the displaced successor's abort is self-reported but not necessarily clean — see §4.6's round-16 rewording.** If the rename-back fails or the path is occupied, leave the file for the janitor (folds as `lock-break-race`), exit `EXIT_LOCK_BREAK_RACE` (19). The successor's lock is never *silently* destroyed — every displacement lands in the sidecar/janitor/trigger machinery.

**Residue:** a releaser suspended > `LOCK_STALE_MS` between steps 1 and 2 can claim a successor's lock — but steps 3-4 detect and recover rather than destroy silently; same disclosed class as §4.5's residue, same self-reported direction (§8).

### §4.10 Detection: mandatory verify-mode triggers (extends §7)

Verify-mode reconcile is **mandatory, not recommended**. **The invocation that transitions a draft into `submitted` — whether `submit` (via `submitting`) or `reconcile` (recovering from persisted `submitting`) — must run verify-mode inline before exiting** if any of:

(a) `attempts[]` contains an `ambiguous` outcome (existing trigger);
(b) `audit[]` contains a `lock-broken`/`lock-break-race` entry whose broken lock had `op: "submit"` or `stateAtAcquisition: "submitting"` (scoped — breaking an idle `edit` lock doesn't poison the draft forever);
(c) `audit[]` contains a `stale-holder-outcome` entry, or an unfolded orphan sidecar exists for this draft;
(d) this invocation recovered the draft from `submitting` (crash-recovery — reachable per the normative recovery procedure below; `resolve`'s human-attested transitions to `submitted` are themselves resolutions and carry no inline verify);
(e) **this invocation's `audit[]` gained one or more `retry-backoff` entries — i.e. any inline 429 retry occurred — even when the `attempts[]` row is `success` (round-15 fix, new trigger).** Rationale in §7: with the unverifiable "429 is pre-processing" claim withdrawn, a retried-then-succeeded invocation is the one path that could create a duplicate while firing none of (a)–(d); trigger (e) closes it regardless of how the vendor question resolves. **Crash persistence:** a `retry-backoff` entry with no later-sequenced verify-result entry (`verify-confirmed`, `verify-inconclusive`, `verify-clear`, `duplicate-detected`, or `verify-network-failed`/`verify-visibility-failed` pending re-run) is an *unsatisfied mandatory verify* — surfaced by `status`, satisfiable by `reconcile --verify` — so a crash between the `submitted` write and the inline verify cannot silently drop the check.

**Crash recovery from `submitting` (normative):** the `approved → submitting` guarded write atomically appends the `attempts[]` row `{attemptId, lockId, startedAt, outcome: "in-flight"}` in the same rename — **cardinality per §2's authoritative definition: exactly one row per submit invocation that persists this transition (round-15 fix — this paragraph previously said "one row per POST attempt," contradicting §2; §2's wording governs and this paragraph now defers to it)**; the same invocation updates that row on final outcome. Any mutating command acquiring the lock over a persisted `submitting` draft refuses and directs to `reconcile` (existing state-error exit code, unchanged). `reconcile` on `submitting`: run the janitor first (§4.7); if a folded sidecar's `attemptId` matches the in-flight row (§2's correlation rule) — `posted: false` ⇒ row `aborted-before-post`, state back to `approved`; `posted: true` with an issue key ⇒ row completed, state `submitted`, `result` set, duplicate evidence handled per the direct-evidence rule below; `posted: true` without a key ⇒ row `ambiguous`. Sidecars with no or mismatched `attemptId` fold as evidence only and do not complete the row. If no sidecar covers the row, set its outcome to `ambiguous`. Then proceed under trigger (d) with mandatory verify and §7's reconcile semantics. Recovery *completes* the existing row; it never creates one.

**Direct-evidence rule:** if `audit[]` contains a `stale-holder-outcome` with `posted: true` and an issue key (or an unfolded such sidecar exists), the gate writes `duplicate-detected` with that key **immediately, with no network search** — and no search-based `verify-clear` can retire it, only `resolve` can. Search-based gating applies only to evidence-free markers (a broken submit-scoped lock, or `posted: true` without a key).

**Marker lifecycle (round-15 fix — the previous lifecycle left trigger-(b)/(c) markers on `submitted` drafts with no terminating path in the *expected* case, since inline verify at maximum index lag normally returns zero matches):** a trigger-(b)/(c) marker is *unresolved* until a later-sequenced `verify-clear`, `verify-confirmed`, `duplicate-acknowledged`, or `duplicate-dismissed` audit entry covers it. The rules for producing those entries:

- **Inline verify** (run by the same invocation that performed the transition — triggers (a), (d), (e)) that returns zero matches writes `verify-inconclusive`, which retires **only** that invocation's own trigger-(d)/(e) marker — never (b)/(c) markers, because a zero-match at the point of maximum index lag is weak evidence.
- **A subsequent, explicit `reconcile --verify` invocation** (a fresh invocation whose purpose is verification, necessarily later than the transition) whose full bounded poll (§7) completes with zero matches writes **`verify-clear`**, retiring all *search-eligible* markers sequenced before it — including (b)/(c) markers. This is the same evidentiary standard the pre-discard/pre-unfreeze gate already applies (zero matches after a completed full poll), and it gives operators the defined closure action `status` names: re-run `reconcile --verify` once the index has had time to catch up. Direct-evidence markers remain excluded from `verify-clear` retirement.
- **`verify-confirmed`** (exact single match equal to `result.key`, §7) retires all search-eligible markers sequenced before it, including (b)/(c).
- A `verify-clear` also means subsequent `discard`/`unfreeze` invocations run no new search unless a new marker has appeared since.
- **None of these entries alters §2's ambiguous-history guard**, whose clearing list (`verify-confirmed`/`duplicate-acknowledged` only) is unchanged — the two mechanisms remain fully independent (see §2).

**Pre-discard/pre-unfreeze gate:** read-only verify-mode search run before `discard` (from **`pending` or `failed`** — round-15 fix: `failed` is now explicitly in scope, closing the reachable uncovered path described in §4/resolve (c)) and before `unfreeze` (from `approved`), audit entries only, never state transitions: zero matches after the completed full poll ⇒ `verify-clear`, proceed; ≥1 match ⇒ `duplicate-detected`, refuse pending human resolution via `resolve` entry state (c) (§4). **This gate keys on `audit[]` evidence and is independent of §2's ambiguous-history guard, which keys on `attempts[]`** — each has its own clearing entries, and clearing one never clears the other. Verify network failure ⇒ audit `{event: "verify-network-failed", at}`; visibility-precheck failure ⇒ `{event: "verify-visibility-failed", at, detail}` (§7 — the check could not produce meaningful evidence and must be re-run; both are distinct from `verify-inconclusive`, which means the search ran and returned zero); `status` surfaces every draft with an unsatisfied mandatory verify; `reconcile --verify` re-runs it.

## §7. Response classification and search-then-retry (final — now exhaustive)

`fetch` invoked with `redirect: 'manual'`.

| Response | State / attempts[] outcome |
|---|---|
| 2xx with `id`+`key` | `submitted` / `success` |
| 2xx without `id`/`key` | `unknown` / `ambiguous` |
| 3xx | `unknown` / `ambiguous` (not `failed` — a redirect doesn't prove no side effect occurred) |
| DNS resolution failure, connection refused, TLS handshake failure (pre-connection failures — deterministically no request ever reached Jira) | `failed` / `failed` |
| 400 (with or without Jira error body) | `failed` / `failed` |
| 401 / 403 / 404 | `failed` / `failed` |
| 408 | `unknown` / `ambiguous` (no inline retry — an immediate retry after "took too long" can't rule out the original succeeding) |
| 429 | inline retry per the `Retry-After` rules below, up to `maxAttempts`; abandonment/exhaustion → `unknown` / `ambiguous`; **any invocation that retried at all arms §4.10 trigger (e), even on eventual success** |
| any other 4xx | `failed` / `failed` |
| 5xx / timeout / connection loss / crash while `submitting` | `unknown` / `ambiguous` (recovery per §4.10) |

**`Retry-After` handling (round-15 fix — the previous `min(Retry-After, timeoutMs * 4)` bound was a direction bug: it *shortened* the server-instructed wait, and a server's `Retry-After` is a minimum, so retrying early predictably earns another 429, burns `maxAttempts`, and can escalate the rate-limit penalty):** the server's `Retry-After` value is honored **verbatim, never shortened**. The cap `timeoutMs * 4` now bounds the client's *willingness to wait while holding the lock*: if `Retry-After` exceeds `timeoutMs * 4`, the invocation **abandons inline retry entirely** — no early retry — and takes the exhaustion path (`unknown`/`ambiguous`, recoverable via `reconcile`, which re-runs the label search without any duplicate risk). A missing or unparseable `Retry-After` header uses a default backoff of `min(2^attemptNumber * 1000, 30000)` ms. All waits are async timers per §4.3's normative constraint; the heartbeat runs throughout.

**429 retry safety (round-15 rewrite — the previous justification is withdrawn, not defended):** the earlier text asserted that 429 "is returned by Jira's rate limiter *before* request processing reaches issue-creation logic — by definition, no issue can have been created." That is not a definitional property of HTTP 429 (RFC 6585 says nothing about whether the request was processed), it is an empirical claim about one vendor's gateway that this design has no citation for, and gateway/proxy-emitted 429s are ordinary counterexamples. **The design no longer depends on it in any direction.** Inline retry after 429 is retained because the design already carries a real idempotency-*detection* mechanism — the `kstack-draft-<uuid>` label on every created issue plus mandatory verify — and §4.10's trigger (e) wires the retry path into it: every invocation that performed any inline 429 retry must run verify-mode before exiting (or, if it crashes first, is surfaced by `status` as an unsatisfied mandatory verify). If a 429 ever *was* side-effecting, the duplicate carries the label and the mandated search finds it — a detected duplicate for a human to resolve, never a silent one. This also resolves the previous internal contradiction: the table's exhaustion row (`unknown`/`ambiguous`) is now coherent, since the design genuinely treats a 429's side-effect status as unknown rather than claiming it is definitionally nil. Whether Jira Cloud's limiter is in fact pre-processing is recorded as a genuinely empirical open item — if implementation-time testing or vendor documentation settles it, trigger (e) becomes belt-and-suspenders, not wrong.

**Search visibility precondition (round-15 fix, Opus SEC-2 — "zero matches" previously conflated "not created" with "not visible to this credential"):** before *any* zero-match result (reconcile or verify mode) is treated as evidence, the invocation must confirm the searching credential can actually see issues in the target project: `GET /rest/api/3/mypermissions?projectKey=<key>&permissions=BROWSE_PROJECTS`, requiring `BROWSE_PROJECTS.havePermission === true`. (Endpoint and parameter shape pinned per current Jira Cloud documentation; **smoke-test at implementation time before reliance** — same discipline as the §4 createmeta pinning.) On precheck failure or a negative result: audit `{event: "verify-visibility-failed", at, detail}`, treat exactly like `verify-network-failed` — the check did not meaningfully run, no zero-match inference is drawn, `reconcile` from `unknown` does **not** return the draft to `approved`, and `status` surfaces the draft. This is the concrete content of the previously asserted-but-unspecified "doctor-proof precondition"; `doctor` runs the same check per configured project. The residual invisibility vector — an issue security level applied via `defaultFields` — is closed at the source by §1's `security` reserved-key ban.

**Reconcile protocol:** visibility precondition above; cursor-paginated label search (`POST /rest/api/3/search/jql`); bounded poll — **lower bound ≥3 probes over ≥30s, upper bound 10 probes or 5 minutes total. Precedence (round-15 fix — with `timeoutMs` up to 120s, three probes can exceed five minutes, and the previous text left the conflict unresolved): the upper bound is a hard deadline and always wins. A probe in flight when the deadline expires is aborted (`AbortSignal`); if the deadline or probe cap is reached before the lower bound is met, the poll is treated as exhausted-inconclusive** (verify-mode's zero-match handling below; for `reconcile`-from-`unknown`, exhaustion without a completed full poll means the draft **stays `unknown`** — the zero-match → `approved` inference below requires a *completed* poll, since an aborted poll is weaker evidence than a completed zero-match one). Zero matches after a completed full poll → `approved` (not refreshing `approvedAt` — a restored approval must re-clear the TTL check). One match → `submitted`. Multiple matches → stays `unknown` (never `failed` — an unresolved external side effect can never reach a discardable state), exit 6, keys recorded in `reconcile-matches` audit entry, human resolves via `resolve`.

**Why reconcile-from-`unknown`'s zero-match handling differs from verify-mode's (two different priors, both correct):** `reconcile` from `unknown` runs when there is **no confirmed prior success** — the POST's outcome was genuinely ambiguous, so zero search matches (visibility-confirmed, full poll completed) is evidence *consistent with* "nothing was created," and returning to `approved` (safe to retry) is the correct inference. Verify mode from `submitted` runs *after* a confirmed 2xx response with an issue key/id already in hand — the POST's success is not in question, only whether the search index has caught up — so zero matches there is index lag, not evidence of absence, and is correctly treated as inconclusive rather than actionable. Same raw evidence, different prior confidence, different — and both correct — conclusions.

**Verify mode** (mandatory per §4.10 triggers (a)–(e), or from `submitted` whenever `attempts[]` has an `ambiguous` outcome, or explicitly via `reconcile --verify`): re-runs the search — except when §4.10's direct-evidence rule already supplied a definitive answer, skipping the search entirely. Runs the visibility precondition first. **Inherits the same bounded poll and deadline-precedence rules as reconcile** — the poll matters more here than in reconcile, since §4.10 mandates inline verify run *immediately* after a submit reaches `submitted`, which is precisely the point of maximum index lag.

- **Exactly one match equal to `result.key`** → `verify-confirmed` audit entry, exit 0, no state change. Retires search-eligible §4.10 markers and clears §2's guard per those sections' rules.
- **Zero matches** (the *expected*, common outcome when verify runs promptly after a genuine, freshly-confirmed success, not evidence of a problem): write `{event: "verify-inconclusive", at}` — not `verify-confirmed` (search absence isn't positive confirmation) and not `duplicate-detected` (there is no duplicate evidence). Exit 0, state remains `submitted`, `result.key` stands as recorded (the original 2xx response with an issue key/id is trusted over a not-yet-indexed search). Marker consequences per §4.10's lifecycle: **from an inline verify**, `verify-inconclusive` retires only that invocation's own (d)/(e) marker; **from a subsequent explicit `reconcile --verify` with a completed full poll**, the result is written as `verify-clear` instead, retiring search-eligible (b)/(c) markers — this is the operator's closure path for the markers `status` surfaces. `verify-inconclusive` does **not** clear the §2 ambiguous-history guard (only `verify-confirmed`/`duplicate-acknowledged` do). Nothing blocks on an inconclusive result — treating the common case as alarming would make verify mode self-defeating.
- **Any other single match, or multiples** → `duplicate-detected` audit entry listing the keys, exit 6, state unchanged; human resolves via `resolve` or cleans up the surplus in Jira directly.

## §8. Hygiene and accepted residual risk (final)

- `.kstack/jira-queue/` added to `.gitignore` (not covered by existing `.kstack/reviews/`/`.kstack/tmp/` entries). Note this entry does **not** protect a credential file placed in-repo — that vector is closed by §1's enforced outside-repo path validation instead.
- `.kstack/decisions/` never receives draft/ticket content — only a post-`submitted` issue key/URL reference if a session wants to record that a ticket was created.
- No queue retention/GC policy in v1 (known limitation, not a gap). `schemaVersion: 1`, no migration logic yet.
- POSIX permission enforcement is best-effort; on non-POSIX-permission mounts (this repo's own `/mnt/e/...`), mode bits may not be enforced — known limitation, `allowInsecurePermissions` is the documented escape hatch (scope limited per §1: mode bits only).
- Every error/diagnostic path routes through the shared redactor already reused by `kstack-reflexion.mjs` from `kstack-memory.mjs`'s secret scanner — never a second implementation. The Basic auth header value is in the redactor's scope (§3).

**Residual risk, layered (final):**

1. **Detected, deterministically given sidecar durability:** any stale holder that resumes and lives long enough to write its sidecar (§4.8) — regardless of when its POST lands or whether the draft was meanwhile discarded (queue-wide janitor sweep, §4.7). A `posted: true` sidecar with an issue key is direct duplicate evidence, no search needed. **"Deterministic" is conditional on sidecar durability: with §4.7's now-normative directory `fsync`, loss requires filesystem-level data loss on a conforming filesystem; on mounts where directory `fsync` is ineffective (drvfs verification pending — open item), durability degrades to the mount's native guarantee and this layer is correspondingly weaker there (round-15 fix: the previous text asserted determinism while directory `fsync` was still an unresolved open item — the two statements could not both stand).**
2. **Detected, via mandatory search:** duplicates landed/indexed by the time of the inline post-submit verify (§4.10 triggers (a)–(e)), a subsequent explicit `reconcile --verify`, or the pre-discard/pre-unfreeze gate. Search-index lag is a named limitation here too.
3. **Genuinely undetected (irreducible, named):** a stale holder whose POST reached Jira but which died between the socket write and the sidecar write, when the resulting issue also lands after every verify point the draft ever passes — requires a lock break *plus* process death inside a narrow window *plus* unlucky timing. Accepted, alongside: the §4.5 microsecond check→rename TOCTOU on local draft writes; the §4.9 microsecond release-claim TOCTOU; the §4.6/§4.9 check-then-rename overwrite TOCTOU (**whose failure direction includes the dirty, self-reported case — see §4.6's honest statement; "accepted" here means accepted as self-reporting, not accepted as clean**); and search-index lag generally.
